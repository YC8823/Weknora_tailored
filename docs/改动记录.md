### 变更内容

| 文件 | 改动 |

| `rerank_server_demo.py` | 模型路径改为 `C:\AI\hf_models\bge-reranker-v2-m3`，端口由 `8001` 改为 `8002` |
| `.env` | 新增 `SSRF_WHITELIST=host.docker.internal` |

### 模型信息

- **模型**：`BAAI/bge-reranker-v2-m3`（568M，中英多语言）
- **权重路径**：`C:\AI\hf_models\bge-reranker-v2-m3`
- **推理服务**：`rerank_server_demo.py`，监听 `0.0.0.0:8002`
- **WeKnora 注册名**：`bge-reranker-v2-m3-local`，Base URL `http://host.docker.internal:8002`

### 部署环境

- conda 环境：`ml-service`（已有 torch 2.7+cu128，CUDA 12.8）
- GPU：NVIDIA RTX 50xx（Blackwell）

### 问题与解决

**1. pip 安装 transformers 失败（SSL 错误）**
企业网络 SSL 深度检测导致 `[ASN1: NOT_ENOUGH_DATA]`，`--trusted-host` 和 HTTP 镜像均无效。
改用 conda-forge 镜像安装：
```bash
conda install --override-channels -c https://mirrors.tuna.tsinghua.edu.cn/anaconda/cloud/conda-forge/ transformers sentencepiece protobuf
```

**2. 启动报 `[WinError 127]`**
`ml-service` 环境中 `torchaudio` 版本与 torch 2.7 不兼容，其原生 DLL 加载失败。新版 transformers 在初始化时无条件导入 `torchaudio`（`loss_rnnt.py`），触发崩溃。
解决：卸载 torchaudio（reranker 不需要音频处理）：
```bash
pip uninstall torchaudio -y
```

**3. SSRF 校验拦截**
`.env` 中 `SSRF_WHITELIST` 默认被注释，导致前端测试连接提示 `hostname host.docker.internal is restricted`。
解决：在 `.env` 中添加（重启容器生效，无需重新 build）：
```env
SSRF_WHITELIST=host.docker.internal
```

**4. 端口冲突 `[Errno 10048]`**
多次启动推理服务时旧进程未退出占用端口。
解决：
```powershell
netstat -ano | findstr :8002   # 找 PID
Stop-Process -Id <PID> -Force
```

## 2026-06-24 修复历史会话打开时 404 流式连接失败

### 问题描述

打开历史会话时，前端弹出"流式连接失败"错误框，浏览器 Network 显示
`GET /api/v1/sessions/continue-stream/{session_id}?message_id=...` 返回 404。

### 根因分析

默认使用内存型 `StreamManager`（`STREAM_MANAGER_TYPE` 未配置时的默认值）。流式事件缓冲区存储在应用进程内存中，容器重启后全部清空。

若某条消息在**生成过程中**容器重启，该消息在数据库中保持 `is_completed = false`。下次用户打开该会话时，前端检测到未完成消息并调用 `continue-stream`，后端在 `StreamManager` 中找不到任何事件，原逻辑直接返回 404，前端展示"流式连接失败"。

正常**已完成**的历史会话不受影响，会话内容完整保存于数据库。

### 变更内容

**`internal/handler/session/stream.go`**：`ContinueStream` 函数，当 `StreamManager` 中无事件时，不再返回 404，而是：
1. 将该消息的 `is_completed` 标记为 `true`（避免下次再次触发）
2. 通过 SSE 向前端发送一个合成的 `complete` 事件，使前端正常退出加载态

### 待优化（方案 B）

当前修复属于兜底处理，中断消息的内容仍为空或残缺。根本解决方案是换用 **Redis 型 StreamManager**：

```env
# .env 中配置
STREAM_MANAGER_TYPE=redis
```

Redis 作为独立容器，应用重启后流式事件仍可恢复，可真正支持断点续传。待后续评估 Redis 资源占用后决定是否启用。

## 2026-07-06 修复远程IP访问权限异常（viewer降权 / 成员管理不可用）

### 问题描述

通过服务器局域网 IP（如 `http://10.34.45.2`）访问 WeKnora 时：

1. 即便是用户本人租户专属的空间，也只有 `viewer`（仅查看）权限，无法进行模型配置等修改，也无法获取租户专属 API Key；
2. "成员管理"功能异常：远程访问时设置菜单里没有这个入口，本机 `localhost` 访问虽然能看到入口，但打开后接口 404。

只有宿主机通过 `localhost` 访问时权限正常，且该现象与具体账号无关——所有账号通过服务器 IP 访问都会复现。

### 排查方向与过程

排查最初怀疑是"根据访问来源（host/IP）判断权限"的后门逻辑，逐一排查并**全部排除**：

- 前端：`getApiBaseUrl()`（`frontend/src/utils/api-base.ts`）恒定返回同源相对路径，不存在写死 `localhost` 的请求目标；全仓库搜索未发现 `window.location.hostname === 'localhost'` 一类判断。
- 后端：鉴权中间件（`internal/middleware/auth.go`）、CORS 配置（`internal/router/router.go`）均未发现基于 `Host`/`Origin`/`ClientIP` 的分支逻辑；CORS 是完全开放的 `AllowOrigins: ["*"]`，并非"仅允许 localhost"。
- `docker-compose.yml` 中 frontend/app 端口均绑定 `0.0.0.0`，`localhost` 和局域网 IP 访问的是完全相同的容器，网络路径无差异。
- "Lite 模式自动登录"分支（`autoSetup`）需要后端编译期 `Edition == "lite"`，标准 docker 部署硬编码为 `"standard"`，确认未触发；`localStorage` 中 `weknora_lite_mode` 实测也为 `null`。

上述方向全部证伪后，转为让用户在浏览器 F12 Network 面板实测复现，逐步定位：

1. 知识库详情页显示"本空间·仅查看"，追踪到前端 `isOwner` 判断逻辑（`frontend/src/views/knowledge/KnowledgeBase.vue`）会在拥有权判断失败时回退显示共享空间角色，而角色数据来自组织（"共享空间"）相关接口。
2. 实测 Network 发现 `GET /api/v1/shared-knowledge-bases` 返回 **500**，`GET /api/v1/organizations` 同样 500，报错内容为：
   ```
   ERROR: relation "organization_members" does not exist (SQLSTATE 42P01)
   ```
3. 检查数据库当前迁移版本：`Current migration version: 51`，而本仓库（`vision-augmented` 分支）`migrations/versioned/` 目录最高只到 `000035`——版本号体系不匹配，说明这个数据库历史上曾被更高版本（上游 `main` 分支）的迁移跑过。
4. 直接查询数据库实际表：未改名的 `organization_members` 不存在，但存在两张"孤儿表"：
   - `organization_members_pre_plan3`：结构与本仓库 `types.OrganizationMember`（`internal/types/organization.go`）逐列完全一致，但空表（0 行）；
   - `organization_tenant_members`：全新的"按租户"成员模型（`main` 分支重构后的结构），仅 1 行数据，正是当前用户自己租户在其组织中的 `admin` 身份记录。
5. 用 `git log --all` / `git merge-base --is-ancestor` 确认：`main` 分支上有 `feat(organization): implement tenant-based access control for organization visibility`（对应 `organization_tenant_members` 新模型）和 `feat(invitations): ...` 等提交，均**不在** `vision-augmented` 分支历史中。同时前端浏览器实测请求了 `/api/v1/user/favorites`、`/api/v1/me/invitations/pending-count`，但这两个接口在 `vision-augmented` 的前后端源码中**完全不存在**——说明实际运行的 frontend 镜像是用 `main` 分支代码构建的，与 `vision-augmented` 分支构建的 backend 镜像不一致。

### 根本原因

两个原因叠加：

1. **数据库结构错位**：早前有人尝试把组织成员模型从"按用户"（`organization_members`）重构为"按租户"（`organization_tenant_members`），重构中把旧表改名为 `organization_members_pre_plan3` 作备份，但重构未完成/被回退，当前代码（`vision-augmented` 分支）仍然按旧模型查询 `organization_members`，导致该表"消失"，所有组织/成员/知识库共享相关接口全部 500。
2. **前后端镜像分支不一致**：frontend 镜像实际由更新的 `main` 分支构建（包含尚未合并进本 fork 的组织权限重构与邀请功能），backend 镜像由当前 `vision-augmented` 分支构建，两边对同一份数据、同一套接口的假设不一致，进一步放大了表现的怪异程度（例如部分页面 404、部分权限判断异常）。

`localhost` 与 IP 访问权限表现不一致，只是巧合关联：本机测试账号很可能从未真正触发过"组织"相关查询路径，因此没有暴露这个早已存在的 500 bug；并非代码里存在按 host 判断权限的逻辑。

### 变更内容（数据库）

仅对空表做重命名和一条历史数据的原样归位，未修改任何业务代码逻辑，未新增/编造任何权限记录：

```sql
-- 1. 结构完全匹配、当前为空的旧表改名回代码期望的表名
ALTER TABLE organization_members_pre_plan3 RENAME TO organization_members;
ALTER INDEX idx_org_members_org_user_pre_plan3 RENAME TO idx_org_members_org_user;
ALTER INDEX idx_org_members_role_pre_plan3 RENAME TO idx_org_members_role;
ALTER INDEX idx_org_members_tenant_id_pre_plan3 RENAME TO idx_org_members_tenant_id;
ALTER INDEX idx_org_members_user_id_pre_plan3 RENAME TO idx_org_members_user_id;

-- 2. 把已经真实存在、只是存错了位置（organization_tenant_members）的
--    owner admin 身份记录，原样搬回正确的表
INSERT INTO organization_members (organization_id, user_id, tenant_id, role, created_at, updated_at)
VALUES ('20a8ed90-adf6-4f27-aa0e-26f8b821f796', 'd62067ad-fae1-4808-9307-82cfdf935497', 10001, 'admin', '2026-06-03 00:26:59.523388+00', now());
```

`organization_tenant_members`（新模型孤儿表，当前代码不引用）保持不动，留作后续确认无用后再清理。

### 改动必要性说明

- **为什么重命名而不是新建空表**：`organization_members_pre_plan3` 的表结构（列、类型、唯一索引）与代码 GORM 模型逐一核对完全一致，且是空表——重命名是"把误改名的表改回来"，风险最低、语义最准确，不存在建了新表却缺历史数据的问题。
- **为什么要手动 INSERT 这一条记录**：这条 `admin` 成员记录本来就真实存在，只是因为半途而废的重构被错误地放进了 `organization_tenant_members`；插入操作是把已存在的真实历史数据原样搬回正确表，字段值（`organization_id`/`user_id`/`tenant_id`/`role`/`created_at`）均取自该孤儿表的原始记录，不是凭空捏造一条权限——这与"直接手动插入一条人员权限记录去掩盖问题"的临时补丁做法有本质区别。
- **为什么要重新构建 frontend 镜像**：确认了实际部署的前端 bundle 会调用本地 `vision-augmented` 分支后端不存在的接口（`favorites`、`invitations`），证明前端代码来自 `main` 分支而非当前签出分支；用当前分支重新构建 frontend，才能让前后端对同一套接口、同一套权限模型的假设保持一致，这也是修复"知识库设置齿轮图标消失"等一系列关联表现的必要前提（重建过程中顺带遇到并解决了 pnpm 安装问题，见下一条记录）。

### 需要重新构建/重启的服务

```powershell
docker compose build app        # 迁移文件已存在于当前分支，重建确保镜像内容与本地一致
docker compose up -d app
docker compose build frontend   # 对齐 frontend 与当前分支代码
docker compose up -d frontend
```

数据库层的表重命名与数据插入直接对运行中的 postgres 容器执行，不需要重启数据库、不影响其他业务数据。

## 2026-07-06 修复 frontend 镜像构建失败（pnpm ignored builds）

### 问题描述

`docker compose build frontend` 在 `RUN pnpm install` 步骤报错：

```
[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: @vue-office/pptx@1.0.1, esbuild@0.28.1, vue-demi@0.14.10
Run "pnpm approve-builds" to pick which dependencies should be allowed to run scripts.
```

### 根因分析

pnpm v10 起默认禁止依赖包运行构建脚本（`postinstall` 等），防范供应链攻击，需显式加入白名单才能执行。本地交互式终端可用 `pnpm approve-builds` 手动批准，但 Docker 构建是非交互式的，无法批准，直接报错退出。

排查过程中先后踩了两个版本坑：
1. pnpm 11 已不再读取 `package.json` 里的 `"pnpm"` 字段配置（会有 `[WARN] The "pnpm" field in package.json is no longer read by pnpm` 提示），需迁移到 `pnpm-workspace.yaml`。
2. **pnpm 11 又把 `onlyBuiltDependencies` 整个废弃了**，改用新的 `allowBuilds` 语法（`pnpm config list` 会把旧字段透传显示，容易误判为"已生效"，但实际安装时并不生效，仍会报 `ERR_PNPM_IGNORED_BUILDS`）。

### 变更内容

| 文件 | 改动 |
|---|---|
| `frontend/pnpm-workspace.yaml`（新增） | 使用 pnpm 11 的 `allowBuilds` 语法批准三个包运行构建脚本：`@vue-office/pptx`、`esbuild`、`vue-demi` |
| `frontend/Dockerfile` | `COPY package*.json ./` 后新增 `COPY pnpm-workspace.yaml ./`，确保构建阶段能读到白名单配置 |

```yaml
# frontend/pnpm-workspace.yaml
allowBuilds:
  "@vue-office/pptx": true
  esbuild: true
  vue-demi: true
```

已通过挂载卷方式跑通完整 `pnpm install`（无 `ERR_PNPM_IGNORED_BUILDS`）验证生效。

### 需要重新构建的镜像

此改动影响 frontend 镜像构建流程，需要执行：

```powershell
docker compose build frontend
```

### 排查中发现的次要问题（未在本次改动范围内）

构建过程中一度复现 `registry.npmjs.org` TLS 握手失败（`ECONNRESET`）。经排查确认是 Docker Desktop/WSL2 网络环境问题（容器内 TLS1.3+HTTP2 握手失败，宿主机直连正常），与本次代码改动无关，用户自行处理网络/VPN。
